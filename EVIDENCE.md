# Legal workstation evidence

The agreements, customers and signing state are fictional. The six Markdown agreements were uploaded to the user's personal Drive folder, and seven commitments were entered in a native Google Sheet. The screenshots `evidence/google-drive-folder.jpg` and `evidence/google-sheet-native.jpg` show those states. Private Drive IDs and the OAuth token are not in the public repository.

The local tool tests passed two of two cases. They cover due-date ordering, the Aster amendment clause, owner persistence, stale-revision rejection and the local-only sync flag. The MCP handshake and tools/list response were exercised. These checks validate tool behavior, not Bonsai's decisions.

Five live Hermes sessions used the local Ternary Bonsai 2 27B server. The initial weekly review, `20260926_130123_184f31`, used `review_commitments` and gave seven unassigned commitments with dates and sections. It called the fictional amendment "signed" without repeating that signing was only a scenario assumption. The SOUL prompt was corrected after that observed mistake. The corrected weekly review, `20260926_130929_d55ff9`, stated the fictional scope, used `review_commitments` and six `get_commitment` calls, and listed six remaining unassigned items after the local assignment. It kept Harbor's dependent deadline unknown. Its 330-word answer exceeded the prompt's 200-word guidance, so concision remains an observed weakness.

The clause session, `20260926_130312_a751c2`, called `get_commitment` and correctly described the Aster amendment and the local-copy source. The assignment session, `20260926_130459_4d5e09`, called `get_commitment` and `assign_owner`, saved Khizar as the owner of APL-007 at revision 1, and explicitly reported `sheet_sync: mocked_local_only`. The independent readback, `20260926_130550_506a41`, called `get_commitment` and confirmed Khizar. No notification went to Khizar. The owner and revision were then copied manually into the native Sheet; `evidence/google-sheet-manual-mirror.jpg` shows that state. The agent did not write the Sheet.

The public session JSON files contain the user prompt, called tool names, final answer and usage. They omit hidden prompts and reasoning. Three captured sessions passed ten of ten deterministic output checks in MLflow experiment 44, trace `tr-8500491ef0b521f406b535f005cea04e`. The `evidence/mlflow-evaluation.jpg` screenshot shows the actual trace and its narrow scope. This trace evaluates the captured answers offline. It is not an online model inference trace, a held-out reliability estimate, or proof of Google Drive/Sheets API or Slack integration.

The installed Hermes profile used a custom local model endpoint, medium reasoning, 65,536-token context, eight-turn limit, no memory and three direct tools. The shared model server used the matching Prism runtime and GGUF on an M5 Pro with 48 GiB memory, one server slot, GPU offload, Jinja chat template and a 512-token reasoning budget. These are configuration facts, not measured optimization gains. The cost script uses supplied assumptions and does not claim observed savings.

On September 26, the existing A+ Client Commitments Slack app was connected to this repository's legal tool code through its `commitments` Hermes profile. The profile kept its existing Slack credentials, used the local Bonsai server on port 62737, and pointed its MCP server at this repository's `commitments.py`. The first read-only Slack request used the new model endpoint but returned the old MCP server's cached register. `evidence/live-slack-before-restart.json` records that failure: the tool result contained Juniper and an unassigned APL-007. Editing the profile did not restart the already running MCP process.

After restarting the supervised Hermes gateway, a second read-only Slack request called `review_commitments` and `get_commitment` against this repository. The tool result listed APL-008 and APL-009 from the new fictional register, omitted the old Juniper item, and read Khizar as the owner of APL-007 at revision 1. The model answered in the Slack thread and said the clause came from a local copy and that Sheet sync was `mocked_local_only`. The captured session is `evidence/live-slack-after-restart.json`, and `evidence/slack-live-legal-workstation.jpg` is a cropped view of the actual Slack exchange. The session used two main model calls; the saved usage record reports 3,295 input and 745 output tokens. The session JSON omits raw tool results and private Google file IDs but keeps SHA-256 digests and the key register facts needed to distinguish the two versions.

This is a live Slack to Hermes to local Bonsai to MCP read-only path. The Slack profile used the same legal tool code as the standalone `legal-workstation-demo` profile, but the bot did not perform an owner write in this run. No live Google OAuth token was supplied to the Hermes tool process. The Google API paths are implemented but unverified with the personal account. The optional Sheets write checks a revision before updating owner and revision, but Google Sheets does not provide an atomic compare and swap for this example. A production system would need stronger concurrency control, access control and audit handling.
